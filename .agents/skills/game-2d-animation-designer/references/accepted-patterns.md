# 复用已认可动画案例

做同类动作前，先查看当前项目的动画案例库（例如 `ProjectKnowledge/15_动画生成知识库.md`，或AGENTS/项目入口指定的路径）。只有当前项目确实存在时才读取；没有案例库也可按通常动作设计流程继续，不为此阻塞任务。

项目案例库维护角色身份、权威PNG、用户反馈、实际参数和验收层级；本skill只保留可迁移的方法。不要从另一个项目悄悄带入角色外观、时间、帧数或用户偏好。

## 已有成功实践：带刀光的单次斩击

动作意图可采用“警戒→后引蓄力→过顶/沿预定弧挥出→接触→随动→收剑”。角色/装备外观输入与运动轨迹输入分别指定用途，避免照搬参考人物。锁定持械手与握点，剑尖路径要可解释；允许受控的快速拖影，不依靠全程常驻光效。

刀光的主弧集中在快速挥出和接触附近；接触位置可有短闪光，之后只留逐渐减少的碎光，蓄力与待机不挂大弧。具体颜色、位置、帧数、时长和力度服从当前任务，不能把一个案例变成所有武器的模板。

无特效/剪影审查是诊断步骤。最终还要看完整身体、武器、特效与游戏背景下的表现；不能因为裸动作更清楚，就自动认定删掉特效的成品更好。用户认可完整效果时，保留其视觉目标，在此基础上解决问题。

生成板必须核验实际alpha、格距和可见内容；身体连通块之外的刀光、碎片、火花可能属于同一帧，不能提取身体时丢弃。整理为透明等格图集，固定根锚点，留足剑尖和特效边距。若输出给Unity，按真实尺寸检查纹理上限和切片次序，序号补零以免拖入Animation时乱序。

最终交付遵循当前项目/用户的已有偏好。用户要单张PNG时，播放与对照可内部检查，不自动附送网页、ZIP或散帧；不反复询问已经明确的偏好。公开的认可层级分清“视觉认可 / 技术检查 / 引擎接入 / 游戏回归”，只写已经获得的证据。

## 接地待机的成功实践

脚底稳定、头腰曲线、披风运动是三个独立的检查项。保持足底位置/朝向和站距可读，允许脚踝以上柔和屈伸；腰先起伏，胸肩/头稍晚响应，布料中段到自由端再延迟。不要为了锁脚而把全身压成近乎静止，也不要用深蹲或全图上下平移替代呼吸。

先选一个完整循环的中性、低点、高点与回程，检查头/腰的高低差及速度变化，再补过渡帧。姿势数与运动幅度分开决定：加帧不能修复僵硬或过深下蹲。已认可的哥布林/其他角色可以借运动机制；外观、比例和服装仍用本角色参考，不照搬另一角色的幅度。

给生成器的输入分别标明身份/画风、运动、布料及构造草案。文本条件反复失效时，增加明确的逐姿势参考或使用可控分层/绑定流程；构造草案须标明非最终角色。分段生成易有尺度、形体及接缝差异，不能只因各段好看就直接拼接。回到整组一致性检查，并记录选/弃依据，不无限重抽同构整板。

披风的S形波浪应从肩部向末端传递，根部跟随躯干，中段与末端错相；检查实际轮廓变化，不把纹理闪动算成布料动画。接地检查也要看左右鞋底轮廓与朝向，不能由根锚点对齐推定每个足部像素被冻结。

环境适配使用场景实际地图作笔触/调色/明暗参考，在近似游戏显示尺寸上看效果；像素绘景观感、严格低分辨率像素网格、PPU/Transform与纹理采样是不同问题。保留用户已认可的动作及角色身份，别在修画风时悄悄重设运动。

用户认可后只将实际选中的图集标为当前案例；生成目标、静态诊断、播放功能检查、用户视觉认可和游戏内回归分别记录。认可不证明数学曲线精确、脚部像素零位移或已经完成引擎接入。


## 在新动作中迁移

先比较动作机制、视角、角色比例、武器握持和玩法时序，再选择可借用的阶段。单斩案例不能直接解决连击、四足步态、飞行或死亡。保留已正确的关键帧，只修出现问题的部位；参考的参数应重新对齐本次Clip，而不是照抄第几帧命中。
