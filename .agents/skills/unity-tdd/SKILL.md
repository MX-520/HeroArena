# Unity 行为测试与 TDD

先定位项目规则、已有接口、测试入口、Unity 和 Test Framework 版本。以调用者能观察的行为为验收目标，复用项目既有测试与诊断流程。

## 选择范围

- 从当前任务挑出关键行为，简述输入、预期结果、测试边界及无法覆盖的部分。现有需求和授权足够时直接实施；仅对会改变玩法语义的缺失信息提问，不把每个测试都变成审批点。
- 优先覆盖容易反复出错的逻辑：伤害/护盾顺序、死亡只触发一次、冷却边界、叠加与到期、禁用/重生清理、存档往返。预期值来自明确规则或独立算例，不复制实现公式作为断言。
- 测试公开行为，不为测试暴露私有字段，不断言无关内部调用顺序。不为小修复迁移整套架构或添加测试框架依赖。

## 一次完成一个行为

1. 新功能先加最小失败测试；缺陷先复现并用测试锁定。确认失败来自目标行为，而非编译、引用、资源缺失或环境问题。
2. 实现足够让该测试通过的改动，再检查受影响的已有测试。逐个行为推进，避免先写整套猜测性测试。
3. 行为通过后，按任务需要做小范围整理并重跑相关测试。已有实现先补覆盖时标明是回归测试，不声称经历过失败到通过。

## Unity 适配

具体测试落点、程序集限制、异步与清理见 [Unity 测试选择](references/unity-testing.md)。纯规则优先 EditMode；需要实际生命周期、物理或多帧联动时考虑 PlayMode。测试模式名称本身不证明覆盖到对应引擎行为。

先检查实际工具是否支持测试执行。缺少 Unity 或测试连接时，可完成已授权的测试代码和静态检查，但明确未执行，不能用模拟输出、普通 .NET 运行或读取旧报告代替 Unity 通过结果。尊重项目对编辑器会话、构建和打包的限制。

## 交付证据

报告改动行为、运行模式/范围、实际结果、日志或结果文件位置及剩余盲区。区分编译成功、测试被发现、测试通过和人工游戏验收。测试通过数为零不代表成功；只做本次影响范围内必要的验证。

来源与适配边界见 [来源](references/sources.md)；不依赖其他第三方 skill 才能使用。
